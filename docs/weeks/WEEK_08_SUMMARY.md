# Week 8 – Part 1: Query Rewriting

## Objective

The objective of Part 1 was to improve the quality of semantic retrieval by introducing a **Query Rewriter** into the Retrieval-Augmented Generation (RAG) pipeline. Instead of directly generating an embedding from the user's question, the system now rewrites the query into a more descriptive and retrieval-friendly form before embedding generation. This helps improve the quality of semantic search while keeping the existing retrieval workflow unchanged.

---

## Architecture

The retrieval pipeline was enhanced by introducing a dedicated **QueryRewriter** component between the user query and the embedding generation step.

### Previous Flow

```text
User Question
      │
      ▼
GeminiEmbedder
      │
      ▼
SemanticRetriever
      │
      ▼
Vector Search
```

### Updated Flow

```text
User Question
      │
      ▼
QueryRewriter
      │
      ▼
Rewritten Query
      │
      ▼
GeminiEmbedder
      │
      ▼
SemanticRetriever
      │
      ▼
Vector Search
```

The `QueryRewriter` was implemented as an independent component inside the `backend/app/rag` package alongside the existing RAG modules (`chunker`, `extractor`, `embedder`, and `retriever`). Its responsibility is limited to transforming user questions into better semantic search queries, keeping the retrieval pipeline modular and following the Single Responsibility Principle (SRP).

---

## Implementation

A new `QueryRewriter` component was implemented with the following responsibilities:

* Accept the original user question.
* Construct a retrieval-oriented prompt.
* Use Gemini (`gemini-2.5-flash`) to rewrite the query.
* Return the rewritten query for embedding generation.

The rewrite prompt was designed to:

* Preserve the user's original intent.
* Avoid answering the user's question.
* Avoid inventing new information.
* Expand vague or short questions into more descriptive semantic search queries.
* Encourage the use of technical terminology where appropriate.
* Leave already clear and specific queries unchanged.
* Return only the rewritten query.

Basic input validation was also added to prevent empty queries from being processed.

---

## Error Handling

Since query rewriting depends on an external LLM, basic error handling was implemented to ensure retrieval continues even if rewriting fails.

The `QueryRewriter`:

* Validates empty user input.
* Falls back to the original user question if Gemini fails to rewrite the query.

This ensures that query rewriting acts as an enhancement rather than a mandatory step in the retrieval pipeline.

---

## Integration with SemanticRetriever

The existing `SemanticRetriever` was updated to internally use the `QueryRewriter` before generating embeddings.

The retrieval process now follows this sequence:

```text
User Question
      │
      ▼
QueryRewriter
      │
      ▼
Rewritten Query
      │
      ▼
GeminiEmbedder
      │
      ▼
Vector Search
      │
      ▼
Retrieved Chunks
```

The public interface of `SemanticRetriever` remains unchanged:

```python
retrieve(question)
```

This allows the rest of the application to continue using the retriever without any modifications while benefiting from improved query preprocessing.

---

## Testing and Validation

A dedicated validation script was created to test the Query Rewriter independently and compare retrieval behaviour before and after query rewriting.

The validation process allows comparison of:

* The original user query.
* The rewritten query generated by Gemini.
* Retrieval results using the original query.
* Retrieval results using the rewritten query.

This provides a simple way to inspect how query rewriting influences semantic retrieval and evaluate whether the rewritten queries produce more relevant search results.

---

## Outcome

By the end of Part 1, the RAG pipeline gained a dedicated **Query Rewriter** that preprocesses user questions before embedding generation. The solution introduces a modular query rewriting layer, integrates seamlessly with the existing `SemanticRetriever`, preserves the retriever's public API, and provides a foundation for improving semantic retrieval quality while maintaining the existing architecture.

# Week 8 – Part 2: Context Builder

## Objective

The goal of Part 2 was to introduce a dedicated **Context Builder** component into the RAG pipeline. This component is responsible for converting the retrieved document chunks into a structured text context that can later be provided to the LLM for grounded response generation.

Unlike the retriever, the Context Builder performs **deterministic formatting only**. It does not retrieve documents, generate embeddings, communicate with Gemini, or produce answers.

---

## Files Created and Updated

### New File

**`backend/app/rag/context_builder.py`**

Implemented the `ContextBuilder` class with the following responsibilities:

* Convert `List[RetrievedChunk]` into a structured context string.
* Preserve the retrieval order returned by the `SemanticRetriever`.
* Format each chunk with source metadata (document name, chunk index, and page number).
* Produce a prompt-ready context string for downstream components.

---

### Updated File

**`backend/app/services/rag_service.py`**

Integrated the `ContextBuilder` into the RAG orchestration layer.

Implemented a new method:

* **`retrieve_context()`**

  * Retrieves the most relevant document chunks using the existing `SemanticRetriever`.
  * Passes the retrieved chunks to the `ContextBuilder`.
  * Returns the final structured context string for future prompt construction.

The existing `retrieve()` method was left unchanged so that other components can still access the raw `RetrievedChunk` objects when needed.

---

## Context Format

Each retrieved chunk is formatted consistently using the following structure:

```text
Source: <document_name>
Chunk: <chunk_index>
Page: <page_number>

<chunk_text>

--------------------------------------------------------------------------------
```

This format provides clear separation between chunks while preserving the original document content and associated metadata.

---

## Testing

A dedicated validation script was created to verify the `ContextBuilder` independently of the database and language model.

The validation covered:

* Multiple retrieved chunks
* Single retrieved chunk
* Empty retrieval results
* Missing metadata
* Preservation of retrieval order
* Correct formatting of the generated context

---

## RAG Pipeline After Part 2

```text
User Question
        │
        ▼
QueryRewriter
        │
        ▼
SemanticRetriever
        │
        ▼
List[RetrievedChunk]
        │
        ▼
ContextBuilder
        │
        ▼
Structured Context String
```

At the end of Part 2, the project gained a reusable **ContextBuilder** component, a standardized context format, and an orchestration method in `RAGService` that prepares retrieval results for the next stage of the RAG pipeline. The generated context will be consumed by the **Prompt Builder** in Week 8 – Part 3.
